## 总结统计

### Token 消耗汇总

| 操作 | 输入Token | 输出Token | 总计Token | 耗时 | 状态 |
|------|-----------|-----------|-----------|------|------|
| v2_init | 304 | 165 | 469 | 116.63s | ⚠️ JSON解析失败 |
| v2_expand | 320 | 30 | 350 | 153.50s | ❌ JSON解析失败 |
| v2_context (1) | **19,962** | 289 | **20,251** | 27.34s | ⚠️ Token异常高 |
| v2_context (2) | **20,756** | 292 | **21,048** | 29.22s | ⚠️ Token异常高 |
| **总计** | **41,342** | **776** | **42,118** | **326.69s** | |

### 关键发现

1. **Token消耗异常：**
   - v2_context 的输入Token异常高（19,962 vs 预期67）
   - 可能是 gemini 模型自动进行了 web search 工具调用
   - 这导致输入token激增，消耗了98.6%的token

2. **时间消耗：**
   - v2_init: 116.63秒（包含重试等待）
   - v2_expand: 153.50秒（包含重试等待）
   - v2_context: 27-29秒（但token异常高）

3. **JSON解析问题：**
   - v2_init: 解析失败，只提取了2个节点
   - v2_expand: 解析完全失败，提取了0个节点
   - v2_context: 解析成功

4. **模型可用性：**
   - deepseek 完全不可用（所有请求都返回502）
   - gemini-3-flash-preview 可用，但会进行工具调用

## 建议修复

1. **直接使用备用模型**：deepseek不可用时，直接使用 grok-4-fast ✅ **已修复**
2. **禁用工具调用**：对于简单的JSON生成任务，不需要web search ✅ **已修复**
3. **改进JSON解析**：增强修复逻辑，处理更多边界情况 ✅ **已修复**
4. **优化Prompt**：减少不必要的上下文，降低token消耗

## 已实施的修复

### 1. 模型切换策略
- ✅ 默认使用 `grok-4-fast`（跳过 deepseek）
- ✅ 如果 grok-4-fast 失败，自动切换到 `gemini-3-flash-preview`
- ✅ 在 `call_ai_with_retry` 中检测到 deepseek 时直接跳过

### 2. 禁用工具调用
- ✅ 在 API 调用中添加 `tools=None` 和 `tool_choice="none"`
- ✅ 防止模型自动进行 web search，避免 token 激增

### 3. JSON 解析改进
- ✅ 增强 `fix_json_string` 函数，处理截断的 JSON
- ✅ 改进字段修复逻辑，从后往前处理避免位置偏移
- ✅ 添加对截断 JSON 的自动修复（在最后一个节点后添加闭合括号）
